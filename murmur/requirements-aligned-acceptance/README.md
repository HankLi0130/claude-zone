# 驗收標準應該對齊提出的需求

## 我的想法

問 AI 問題時請 AI 產生解法，要驗證該解法必須跟問的問題是同一個 level

例如：
幫我生產一個便當，裡面要有三菜一肉一飯，那我驗證的範圍就是便當裡有沒有三菜一肉一飯，至於三菜是哪三菜、肉是什麼肉、飯是白米還是糙米，這就讓 AI 自由發揮或是多加規範

我認為網路上常說的不看程式碼，也是同樣的道理，如果只定義系統應該達到哪些需求、完成哪些目標，沒有多加規範的話，那就只能驗證當初提出的需求跟目標，至於程式怎麼寫、架構怎麼做就是由 AI 自行發揮

## Claude 補充

### 隱性需求

- 便當要「三菜一肉一飯」，但沒人會寫「菜不能是壞的」「飯要煮熟」，這些是默契。三個爛掉的菜也滿足規範，你卻不會接受。軟體裡這類默契更多。
- 安全性、效能、可維護性、不要把 API key 寫死、不要用已淘汰的套件。

### 「不看程式碼」的真正意思

- 是人不看，機器看。
- 型別檢查、lint、測試、靜態分析、依賴掃描。
- 把規範層級以下的驗證自動化，讓人的注意力真的可以停在需求層。
- 想做到不看碼，前提是先把「壞掉的菜」這類隱性需求變成可執行的檢查。

### 看程式碼有時不是在驗證，是在修正規格

- 原本不在乎白米糙米，看到糙米才發現自己在乎——這是需求探索，不是驗收失敗。
- 等規格穩定了、隱性需求都被寫進 gate 之後，才有資格不看。

## ChatGPT 補充

### 驗證可以深入不同層次

| 要確認的事情 | 例子 | 我的看法 |
|---|---|---|
| 是否完成明確需求 | 正確的 OTP 可以登入，錯誤的不能登入 | 必須驗證 |
| 是否符合事先約定的工程限制 | 不新增服務、沿用既有資料庫、遵守專案規則 | 有約定就必須驗證 |
| 是否符合個人的實作偏好 | 函式要怎麼拆、使用哪個設計模式 | 沒有規範，就應給 AI 空間 |

- 如果某個架構要求真的重要，就應該把它變成明確的約束，而不是期待 AI 自己猜中。 
- 約束也不必每次重寫，可以放在專案規則，作為每個任務共同的前提。

### 沒規範的部分，人仍需再檢查

- **需求可能漏寫。** 看到實作才發現少了一個重要條件，應該補需求、再調整解法。這是需求逐漸明確的過程。
- **驗證可能不足。** 幾組測試通過，只能證明那些情境通過。例如，先後送出兩次請求與同時送出兩次請求，未必是同一個情境。

### 「不看程式碼」的真正意思

- 人可以不親自檢查所有實作細節，但需要足夠的證據，支持對結果的信任。 
- 證據可以來自行為測試、自動檢查、其他人的 review
- 針對重要部分閱讀程式碼。閱讀程式碼是其中一種手段，不必成為每個任務的固定儀式。
