# 在 Claude Code 中選擇 Claude 模型與努力程度（Effort Level）

**重點摘要：**

* Claude 模型選擇決定了一組固定的權重（Weights），即模型的整體能力範圍。雖然可以為模型提供上下文或進行引導，但模型的整體知識庫與能力是固定的。
* 努力程度（Effort）的意義不僅僅是「思考時間」。它控制了 Claude 在處理您的請求時整體投入的工作量，包括讀取的檔案數量、使用的工具，以及在回頭向您確認之前所執行的步驟數量。
* 針對較為常規的任務選擇較小的模型，針對較複雜或模糊的任務選擇較大的模型。
* 從每個模型的預設努力程度開始，並根據您進行的工作類型將其作為一般偏好進行調整，而不是逐個任務進行調整。
* 如果 Claude 具備所有相關上下文，顯然已經盡力了，但仍然出錯，這表示需要選擇能力更強的模型。
* 如果 Claude 是因為略過檔案、未執行測試，或在重構進行到一半時放棄而出錯，請選擇更高的努力程度。

## Claude Code 努力程度與模型選擇

Claude Code 提供了兩個看似能「讓回答更好」的設定：模型設定與努力程度（Effort level）。您可能會預期像 Claude Fable 5 這樣更大的模型會比 Claude Sonnet 提供更聰明的輸出，而更高的努力程度意味著 Claude 在回答前會思考更長的時間。

第一個假設是準確的。根據業界標準基準測試，我們最大的模型確實能力更強。

但努力程度不僅僅意味著「思考時間」。努力程度控制了 Claude 在處理您的請求時整體投入的工作量。這確實包括模型思考的時間長短，但也包括：

* 它讀取了多少檔案；
* 它驗證了多少內容；以及
* 在回頭向您確認之前，它在多步驟任務中推進了多遠。

在較高的努力程度下，Claude 在回報給您之前會採取更多這類行動（例如：讀取檔案、執行測試以及重複檢查）。在較低的努力程度下，它寧可向您詢問更多上下文，也不願消耗 Token 來自行釐清問題。

## 模型選擇的運作方式

當您按下 Enter 時，Claude Code 會將您的訊息與 System Prompt、工具定義、您的 `CLAUDE.md`、對話紀錄以及上下文中的任何檔案組合在一起。所有這些內容都會作為單一請求發送到 API。

不過，模型絕不會將其視為純文字。伺服器上發生的第一件事是 Tokenization（詞元化）；文字被拆分成片段，每個片段都會被映射到模型訓練時使用的固定詞彙表中的一個整數。`const` 可能映射到 1978，`await` 可能映射到 4293。從此刻開始，您的 Prompt 就是一個整數陣列。

模型的工作是接收該陣列並預測下一個出現的 Token 是什麼。它的做法是計算其詞彙表中每個 Token 的機率，並從最高機率中挑選。在 `const x = await` 之後，訓練良好的模型會將高機率賦予 `fetch`（非常可能），而將接近零的機率賦予 `banana`（完全不可能）。

將您的輸入 Token 轉化為這些機率的關鍵在於權重（Weights，也稱為 Parameters）。這些是組織成大型矩陣的數十億個數字。為了預測一個 Token，模型會讓您的輸入通過這些矩陣——一長串的矩陣乘法——並在最後讀取機率。權重就是模型所「知道」的一切存放之處。

每個模型的權重都是在訓練期間設定的，當您發送請求時，它們已經是唯讀的（Read-only）。您的 Prompt、您的 `CLAUDE.md` 或您的上下文都無法改變它們。（如果您聽過 Inference「推論」這個詞，它指的就只是：在訓練完成後，以固定的權重使用模型。）

Claude 對於 TypeScript、熱門框架、慣用語法 Go 或任何其他通用程式設計知識的所有了解，都在訓練時被編碼進了這些權重中。

您的 Prompt 和上下文仍然可以引導預測（將您的真實程式碼放在 Claude 面前就是一種引導，而且效果非常好），但它們不會在權重本身中添加任何東西。

如果某個 Library 在模型訓練時並不存在，它就不在權重中。您可以將文件放入上下文中，Claude 會使用它們，但那是引導，而不是教學。Claude 的回應只會在該次請求中受到影響；底層模型並未保留該資訊。

因此，當 Claude 自信地呼叫了一個不存在的 API（即 Hallucination，幻覺）時，那是權重根據訓練模式產生了一個看似合理的 Token 序列，而不是查詢失敗。

那麼，更換模型究竟改變了什麼？它更換了處理您請求的那組凍結權重。

模型不會一次生成整個答案。它預測一個 Token，將其附加到序列中，然後再次執行整個計算以獲得下一個 Token。一個 200 個 Token 的回應就是 200 次獨立通過權重的計算。這個迴圈正是您大部分等待時間和輸出成本的來源。

因此，模型設定決定了由哪組權重來處理您的請求，同時也決定了每個輸出 Token 的成本。

它無法決定的是生成了多少個 Token。對於同一個 Prompt，這個數量可能會因 Claude 決定投入多少工作量而有很大差異。

這就是努力程度所控制的：Claude 決定在每個回合（Turn）中投入多少工作量。

## Claude Code 努力程度的運作方式

當 Claude Code 處理任務時，它生成的 Token 分為幾個類別：

* **Thinking（思考）：** 您在各個行動之前和之間看到的串流推理過程。
* **Tool calls（工具呼叫）：** 指明像 `Read` 或 `Edit` 等工具及其參數的結構化區塊，Claude Code 隨後會解析並執行這些工具。
* **Text to you（給您的文字）：** 計畫、進度更新、最後的摘要。

這些都是來自同一個迴圈的普通輸出 Token，計費費率相同。例如，思考 Token 的生成方式與其他輸出 Token 完全相同，並在該回合的剩餘時間內保留在上下文中。

當 Claude 轉向撰寫程式碼時，它早期的推理就像它讀過的檔案一樣，成為輸入的一部分。

努力程度如何改變這些？努力程度會作為請求的一部分，與您的 Prompt 一同發送給模型。模型經過訓練，能夠理解在每個努力程度下應如何表現，而這種學到的行為已融入凍結的權重中。

當您的請求到達時，努力程度是模型響應的另一個輸入，就像它響應您的 Prompt 文字一樣。這為 Claude 設定了行為標準，決定在它認為任務完成之前需要達到何種程度的徹底性與確定性。

每一回合都會考量這一點，並產生更多 Token 以產出更高信賴度的答案。

在較高的努力程度下，Claude 通常會從制定計畫開始，而努力程度會影響該計畫的深度與廣度。然而，計畫並非一成不變。隨著 Claude 從其行動中獲得結果，它會更新已取得的進度以及對累積結果的確定程度。

因此，當一個三項假說的除錯計畫在步驟 1 就找到 Bug 時，「調查假說 2 和 3」可能就不再是必要的行動。Claude 通常會明確表示：「第一次檢查就找到了問題，因此不需要進行其餘檢查」，然後直接跳過。您會在 Claude Code 中看到這種情況，任務清單會在執行途中進行修正。

在較高的努力程度下，Claude 會更傾向於重複檢查其他假說或驗證正確性，但對於簡單的任務，它通常不會在較高努力程度下人為灌水使用量。事實上，我們的團隊在模型訓練期間密切關注「過度思考」（Overthinking），因為它會降低效率。

## 選擇努力程度

我們的建議是，對於大多數任務，您應該使用模型的預設努力程度。預設值是 Claude 會根據大多數人願意在任務上花費的成本來調配其 Token 使用量的層級。

將努力程度視為手動覆寫控制，以調整 Claude 工作的努力程度與時長。當您根據自己的領域或從事的工作類型對徹底性或速度有強烈偏好時，請刻意選擇它。將此視為一種一般偏好，而非逐個任務做出的決定。

在 Claude Opus 4.8 推出後，有一些實用見解可能有助於引導您：在我們的測試中，我們發現當您對 Opus 4.8 使用預設努力程度設定時，相較於在相同任務上使用 Opus 4.7 的預設努力程度設定，它會以大致相同數量的 Token 產生更好的結果。

## 當 Claude 出錯時該調整什麼

當 Claude 出錯時，您的第一反應不應該是調整旋鈕，而是檢查您提供的上下文。您的 Prompt 是否太模糊？Claude 是否連接了正確的工具？是否配備了適當的技能？

如果您在一個本不該需要提高努力程度的任務上提高了努力程度，解決方法通常在上游——在您的上下文、您的 `CLAUDE.md` 或任務範疇的界定方式中。

但假設您已經提供了清晰的上下文，而 Claude 仍然出錯，您需要問自己的問題是：它是努力不夠，還是知道得不夠？

### 模型：問題太難了

當問題確實很困難時，請選擇較大的模型。例如，難以捉摸的 Bug、陌生的領域或架構決策等問題。在無論給較小模型多少上下文，它都會非常自信地犯錯的情況下，較大的模型會很有幫助。

較大的模型也更擅長處理模糊性，而在較小的模型上，引導執行的具體指示則是邁向成功的更好方針。

當工作屬於常規性質時，請選擇較小的模型。例如，您可以精確描述的編輯、機械式的修改，或關於已經在上下文中的程式碼的問題。沒有理由為任務不需要的能力付費。

如果 Claude 具備所有相關上下文，顯然已經盡力了，但仍然出錯，這表示需要選擇較大的模型。如果您使用的是較大的模型，而且工作已經常規化了一段時間，那麼調低模型將提高速度，並且通常可以在不影響輸出品質的情況下降低成本。

### 努力程度：Claude 努力不夠

如果 Claude 出錯的原因是略過檔案、未執行測試或未重複檢查其工作，請選擇較高的努力程度。如果您選擇的努力程度低於模型的預設值，這一點最為相關。

## Fable vs. Opus vs. Sonnet：專科專家、領域專家與全功能通才

我喜歡這樣思考這兩個設定之間的關聯：Fable 是見過幾乎沒人見過的問題的專科專家，Opus 是領域專家，而 Sonnet 則是非常優秀的全功能通才。努力程度決定了他們之中任何人花在您任務上的時間。

低努力程度的 Opus 就像是能與一位在您這類問題上有深厚經驗的專家進行五分鐘交談。他們帶來了您程式碼庫中任何地方都沒有的知識：他們以前見過的模式、知道要檢查的陷阱，以及只有從解決過大量類似問題中才能獲得的經驗。但只給他們五分鐘意味著對您的程式碼進行快速瀏覽，而不是仔細閱讀。

高努力程度的 Sonnet 就像是給一位非常優秀的通才整個下午的時間。他們會閱讀所有內容、執行程式、重複檢查他們的工作，並最終徹底理解您的特定程式碼。他們較欠缺的是那種「我以前完全看過這種情況」的敏銳辨識力。

Fable 即使在低努力程度下，也像是那位一眼看過每個人都卡住的問題、卻仍能發現沒有其他人會注意到的事情的專科專家。這種辨別能力是您付費最高的部分，因此值得將其保留給真正需要的任務。

這些模型沒有哪一個是絕對更好的。模型設定大致代表「有多大能力」；努力程度設定大致代表「有多徹底」。大多數實際任務兩者都需要一些。

## 努力程度、模型與 Token 消耗

那麼模型選擇、努力程度與 Token 消耗之間究竟是如何相互作用的？這取決於任務本身。

在相同努力程度的常規工作上，兩種模型通常都能做好。較大的模型會因為額外的驗證步驟而消耗更多 Token，且每 Token 價格更高。這就是為什麼在常規任務期間降至較小的模型可以在不犧牲品質的情況下真正節省費用。

在較困難的多步驟工作上，情況就不同了。較小的模型必須勉強逼近其能力極限，耗費大量迭代次數，而較大的模型則能以更少的步驟達到相同的品質標準。

雖然您為較大的模型支付更高的每 Token 單價，但在確實超出較小模型能力的任務上，每個任務的總成本反而可能更低。此外，更重要的是，較大的模型可以完成較小模型即使在最高努力設定下也無法完成的任務。

這在 Fable 上表現得最為明顯。在長篇多步驟的工作中，它領先得最多。在我們的測試中，它完成了 Opus 和 Sonnet 在任何努力程度下都無法達成的任務。它的每 Token 成本也是最高的，這也是為什麼要將它留給真正需要的工作的另一個原因。

上述圖表中的關鍵在於：努力程度選擇了 Claude 願意沿著曲線前進多遠，但這並不意味著 Claude 一定需要走那麼遠才能完成任務。

對此還有另一個細微差別：努力程度塑造了 Token 消耗，但並未限制它。系統中唯一的硬性上限是 `max_tokens`，一旦觸發，它會在串流傳輸途中截斷回應。這是一種生硬的工具，主要與 API 開發者相關。較為柔性的控制方式（例如任務預算或在 Prompt 中要求 Claude 保持簡短）是更有幫助的工具。它們作為模型經過訓練會遵循的指導方針——如果接近限制，它會尋求結束任務——而不是一道它會直接撞上的牆。

## 從預設值開始，再視需求調整旋鈕

大多數時候，您不應該去煩惱這兩個設定。當結果未達預期時，請捫心自問：「是 Claude 知道得不夠，還是它努力得不夠？」並根據需要進行調整。
