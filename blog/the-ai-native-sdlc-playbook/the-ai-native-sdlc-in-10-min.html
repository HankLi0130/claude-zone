STAGE 01 / PLAN

人類說問題，Claude 整理意圖。

先確認「為什麼做」，留下 intent.md

01

與傳統不同從多次會議與轉述，轉為人類直接和 Claude 討論、確認需求。

HOW / 怎麼分工

  1. 人類用人說的話描述問題，暫時不急著選技術。
  2. Claude追問使用者、目標、限制，以及不做的範圍。
  3. Claude產出 intent.md，列出未解問題。
  4. 人類修正誤解，決定是否接受這項需求。

我們需要一個 Login API

「讓使用者提交 username 和 password，登入後才能使用受保護的功能。」

Claude 追問：帳號已存在嗎？成功後回傳什麼？包含註冊嗎？

人類確認

這次只做登入；不做註冊、登出與忘記密碼。

↗ 有沒有效？需求記錄更快；開發後「不是我想要的」改寫更少。
✓ 何時進入 Design？人類接受 intent.md；目標、限制及未解問題清楚。

STAGE 02 / DESIGN

Claude 提規格，人類決定行為。

將意圖轉成能驗收的 spec.md

02

與傳統不同從需求與設計逐次交接，轉為 Claude 整合規格、提早標出衝突。

HOW / 怎麼分工

  1. 人類提供 intent.md、現有系統背景與規範。
  2. Claude提出 API 行為、錯誤情境、選項與疑問。
  3. 人類決定取捨，處理重要疑問與規範衝突。
  4. Claude整理 spec.md，由人類確認並核准。

把「登入成功」說具體

POST /login
{
  "username": "bookclub",
  "password": "••••••••"
}
200驗證成功，回傳 access_token400缺少必要參數401帳號不存在或密碼錯誤：相同訊息

沿用既有 password hash 機制；確認 Token 效期；Log 不含密碼或完整 Token。

↗ 有沒有效？規格完成更快；Build 後因規格模糊而重做更少。
✓ 何時進入 Build？人類核准 spec.md；行為可驗收，阻礙實作的疑問已解決。

STAGE 03 / BUILD

先看計畫，再讓 Claude 動手。

人類核准 plan.md，Claude 依計畫實作。

03

與傳統不同從工程師自行構思與實作，轉為 Claude 先提可檢查的計畫，再執行。

HOW / 怎麼分工

  1. 人類提供 spec.md，要求以 plan mode 分析。
  2. Claude閱讀 codebase，列出檔案、順序、風險與驗證方式。
  3. 人類追問「會破壞什麼？」確認並核准計畫。
  4. Claude實作與測試；重要偏離由人類確認。

Login API 的修改路線

01查閱 Router、帳號查詢、密碼驗證
02新增 Handler，檢查 username / password
03比對 password hash，產生 Token
04補上成功、失敗與錯誤處理測試
CLAUDE.md · 須知Skills · 知識Hooks · 檢查

文件提供指引；必須強制遵守的限制，需要 Hooks、CI 或權限控制。

↗ 有沒有效？合併時間縮短、重做更少；實作符合計畫。
✓ 何時交給驗證？變更可驗證、附對應測試；計畫差異已說明與確認。

流程穩定後，再用 worktree 或 subagent 分工；同時執行的任務量，以人類能有效 Review 為限。

STAGE 04 / TEST

「完成」要附上證據。

Claude 執行檢查，人類判斷證據是否足夠。

04

與傳統不同從等待後續測試回報，轉為 Claude 持續驗證，並用 Evals 評估 Agent 設定。

HOW / 怎麼分工

  1. 人類確認驗收情境，提供 Build、Test、Lint 指令。
  2. Claude補齊測試、執行檢查並修正問題。
  3. 工具產生真實結果，執行必要限制。
  4. 人類檢查 Claude 回報的結果與未驗證部分。
Tests這次產出的 API 對不對？
EvalsAgent 設定變更後，能力退步了嗎？

驗證完整的登入行為

情境預期
正確帳號與密碼200 + Token
缺少必要參數400
帳號不存在 / 密碼錯誤401
Token 呼叫受保護 API正確身分
檢查 Log無敏感值

表中是驗收目標，不是實際測試結果。回傳 200，不代表整個登入功能已驗證完成。

↗ 有沒有效？CI 首次通過率提高；基本錯誤與上線後缺陷減少。
✓ 何時進入 Deploy？必要檢查通過、需求有證據；已知問題已妥善處理。

檢查「跑了什麼、結果是什麼、是否涵蓋需求」，也要防止 Claude 為了通過而削弱測試。

STAGE 05 / DEPLOY

Claude 準備，人類核准上線。

PR Review、修正、發布準備，都在這一站。

05

與傳統不同從人類承擔大量檢查與準備，轉為 Claude 協助處理，人類集中判斷風險。

HOW / 怎麼分工

  1. 人類定義 Review 標準與發布核准條件。
  2. Claude檢查 Bug、安全與規格一致性；修正回饋。
  3. 人類檢查重要邏輯與風險，完成必要核准。
  4. 工具執行 Gate，依核准流程部署並保留紀錄。

Production 前，有一道 Gate

Claude · Review 與修正能繞過密碼驗證嗎？Token 身分正確嗎？
人類核准發布
Claude 不能自行跳過
工具 · CI/CD 部署基本檢查 + 監控 + 已驗證的 Rollback

AI Review 協助分配注意力；高風險邏輯仍需要適當的人深入檢查。

↗ 有沒有效？Review 等待縮短；缺陷提早攔下，部署失敗率不升高。
✓ 何時進入 Maintain？核准完成、部署與基本檢查成功，監控及 Rollback 就緒。

STAGE 06 / MAINTAIN

讓真實世界的回饋，回到流程。

工具觸發、Claude 分析，人類決定處置。

06

與傳統不同從等待人類開始調查，轉為監控或排程觸發 Claude，再經授權路徑修正。

HOW / 怎麼分工

  1. 人類定義指標、觸發條件與 Claude 的權限。
  2. 工具按明確規則偵測異常，觸發 Claude。
  3. Claude分析 Log 與變更，提出有證據的診斷。
  4. 人類決定修正、排程或忽略；Claude 依授權開 PR 或建立 intent.md。

Login API 的 5xx 突然增加

異常觸發→分析證據→決定處置

Claude：「可能是資料庫連線錯誤未妥善處理，以下是相關紀錄……」

診斷是待驗證的假設。圖表僅為流程示意，非實際監控數據。

↗ 有沒有效？診斷更快、有效修正更多；誤報與同類事故減少。
↻ 何時回到 Plan？問題值得處理且有證據；大變更建立 intent.md，小修正走 PR。

修正後補上 Tests 或 Evals，由人類確認；Maintain 在系統運作期間持續進行。
